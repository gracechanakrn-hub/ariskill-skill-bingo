## 3. Strengths to preserve

- **Pool eligibility (D-06, BR-08, AC-4).** `pool.js isEligibleSkill` = `status === 'active' && (isCore || isCritical)` at the skill level; `buildDrawPool` = unique eligible skills on `LOCKED_ACTIVE` boards, snapshotted into `rounds.pool_json` at lock and reused by start and every draw; start is refused below 5 (`POOL_TOO_SMALL` -> E20, transaction rolled back so `start_now` leaves the round open); `boardCanWin` powers the A-03 "no board can win" warning; nothing ever widens the pool.
- **Unbiased, unique draws (BR-09, BR-10, AC-5).** Production uses `node:crypto randomInt` (rejection-sampled, uniform) over the sorted remaining pool; `BINGO_RNG_SEED` makes the process refuse to start in production (`config.js`) and is keyed by (seed, event, round, draw) elsewhere so fixtures replay; `UNIQUE(round_id, skill_id)` and `UNIQUE(round_id, number)` are enforced by SQLite, not only by code.
- **No client or admin influence.** `round.draw.next` carries no skill (the admin client strips params in `commands.js sanitizeParams`; the server ignores them); positions come only from the server; matches are computed server-side and pushed as `myMatchedPositions`; the mobile state module never infers lock/start/winner; time is server-corrected with E7 fallback.
- **Atomic winner close (BR-13..BR-15, AC-7).** One `BEGIN IMMEDIATE` transaction covers draw insert, match rows, evaluation of every `LOCKED_ACTIVE` board with cumulative masks, winner rows (`PRIMARY KEY(round_id, participant_id)`), state -> `WINNER`, version bump and outbox; publish happens after commit; `WINNER` accepts no commands; `expectedVersion` + `(Idempotency-Key, actor, body hash)` turn two simultaneous clicks into one draw (e2e verified).
- **Draw-five threshold (BR-12, AC-6)** is a pure function of the accepted draw number (`isEvaluationActive`) with boundary tests for 1-4 vs 5 and 17.
- **Exhausted handling (E11/E23).** The last draw without a winner moves to `EXHAUSTED` inside the same transaction, Souls are still created for every active board (BR-16), admin gets `Close round` with E23 + E11, public/stage show the round-complete notice.
- **Lock atomicity and deferrals (BR-06, BR-07, AC-3).** READY -> `LOCKED_ACTIVE` and DRAFT -> `DEFERRED` in one transaction with an active-count invariant; `lock_at` elapsed already rejects edits even if the transaction failed; cancelled rounds defer every live board with reason `cancelled`; `openRegistration` reassigns deferred boards as fresh DRAFTs (positions cleared, new finalize = new layout) and skips participants who already have a board; the client auto-finalizes reassigned 25-sets.
- **Pseudonym policy (OD-03).** Consented display name else a stable `Soul #NNNN`; the D-19 fix keyed it by the real participant id and the seeded test asserts both label kinds in `result.published` across public/stage/admin/participant streams.
- **Soul and Float (BR-16, BR-17, AC-11).** Seed from (event, participant, round) only; `validateSoulConfig` rejects forbidden inputs and falls back to the neutral Soul; the Bingo Star is a separate badge; Float consumes via `UPDATE ... WHERE consumed_at IS NULL AND expires_at > now`, replays return the original entrance, token hash only for lookup.
- **Pacing defaults (D-10, OD-04..06)** are configuration, never automation: 12 s result window clamped 10-15, 60 s overdue warning with no auto-start, 5-8 s hint with manual Next Skill only.
